# 通用 Skill 能力扩展方案（讨论稿）

日期：2026-10-20。依据：用户提供的 Cursor 对话、nero-agent 当前源码、参考项目本地源码、Agent Skills 官方规范及本项目已安装 Mastra 文档。

更新：用户已明确将 Bash、公开网络、任务内安装依赖作为正式需求。下文保留原分析过程，但其中“默认离线、运行时不安装依赖”的推荐已被 [新版正式设计](superpowers/specs/2026-10-20-sandbox-public-network-design.md) 替代。新版设计已获用户确认；代码和验证情况见 [验收记录](sandbox-public-network-verification.md)。

本文是分析与建议，不表示能力已实现或已经验收。未修改运行代码，未运行 PPT 包。用户未提供 ppt-master.zip，因此不对其具体依赖和执行结果作保证。

## 1. 目标和边界

目标是让通用 skill 包能以较少改动接入：按需加载说明和资源、运行附带脚本或任务生成的代码、处理文档与数据、获取公开素材、检查结果并交付文件。PPT 是验证案例，不是平台唯一用途。

不纳入 Hive、OneSQL、内部血缘等业务系统，不引入用户登录态传递。默认沿用现有离线执行方式；公开网络和 AI 生图等能力通过平台工具提供。无需为了这个目标重写已有技能管理系统。

“支持 SKILL.md 格式”“脚本能够运行”“完整工作流能够完成”是三个不同承诺，产品状态和验收要分别表达。

## 2. 对 Cursor 结论的校正

正确的部分：当前脚本容器无网络；镜像未显式安装文档处理依赖；run_skill_script 要求 scripts/ 下的已声明入口；当前不能承诺这份 PPT 流水线完整可用。

需要修正或补充的部分：

1. **不是只有 run_skill_script 才能执行代码。** 项目已有 execute_command，沿 SandboxManager → Docker engine 以 command + args 执行。通用容器只挂载用户 workspace，技能容器额外挂载 /skill；二者没有统一的 skill 可见性。不能将入口白名单当作整个 Agent 的代码执行边界。
2. **只读根文件系统不等于不能生成文件。** /workspace 可写，/tmp 是可写 tmpfs。venv 也可以位于可写路径；当前禁止运行时安装是部署策略与环境约束，不是 Docker 只读根必然导致。
3. **ZIP 导入和包内 ZIP 是两回事。** previewSkillZip 已支持外层 ZIP 导入与展开；内嵌 ppt-master.zip 当前作为普通二进制资源保存，不会自动展开。不能笼统说项目不支持 ZIP。
4. **依赖不能只凭脚本名确定。** SVG → PPTX 不一定使用 python-pptx，也可能涉及自定义 OOXML、渲染器或其他工具。需要实际脚本才能给出准确依赖锁定清单。
5. **补库不等于恢复完整流程。** 还涉及字体、系统二进制、附件路径、脚本参数、超时、预览、生图接口、交互等待与恢复。
6. **server-tools 不是脚本代理网络。** 声明它不会让 requests/fetch 自动转成平台工具调用，联网脚本仍需显式适配。
7. **没有 ZIP 可以做架构判断，有 ZIP 才能验收具体技能。** 目前能够确定的是未具备完整运行条件，不能证明每个未知脚本都一定失败。

参考项目提示词明确要求 Python、预装库和工作区 venv；SkillTool 返回 /primeai/skills/<name> 目录。它体现了“文件目录 + 通用执行环境”的模式，但提示词不等于本次已验证的实际容器环境。

## 3. 方案选择

| 方案 | 收益 | 代价与适用性 |
| --- | --- | --- |
| 仅扩充现有镜像、逐个改写 skill | 最快跑通少数已知技能 | 每个包继续适配，难覆盖动态代码、依赖差异和预览；适合作为首个里程碑 |
| **标准包兼容 + 受控通用运行环境** | 保留已有治理，同时让多个技能复用执行、资源和产物能力 | 需要增补运行环境注册、路径绑定、预检和文件交付；推荐 |
| 完整复制参考项目的自由 shell、联网安装模式 | 更接近其脚本使用习惯 | 需要重审现有部署约束，且仍不能提供缺失的服务、字体与 UI；当前不推荐 |

推荐方案以第二种为目标，先用第一种的工作量做出最小闭环。通用性应来自可扩展的环境和工具契约，不是无限大的预装镜像。

## 4. 保留现有技能治理

继续使用 skills 下已有的权限、草稿、发布、不可变 release、manifest hash、run pins、回滚、审计和清理机制。继续使用应用自有 skill / skill_read / skill_search，避免与 Mastra 原生自动工具并行注册。

Agent Skills 标准规定 SKILL.md 元数据和按需读取的资源结构，不规定必须使用某个执行工具，也没有要求 skill-runtime.json。后者应作为 Nero 的可选运行配置，而不是所有外部 skill 必须手写的前提。

没有运行配置的包依然可以导入、阅读和做预检，但不能静默获得脚本执行权限。平台可生成候选配置，发布流程确认后生效。

用户粘贴的 PPT 正文没有展示 YAML name / description。若原文件也缺少，当前导入校验会失败；若只是复制时省略则无需处理。

## 5. 包与路径兼容

保留 scripts、references、templates、assets、workflows 等完整目录；不要为了符合自定义分类移动所有资源。默认展开外层 ZIP。包内 ZIP 先报告内容缺失或待展开，提供显式展开预览，校验大小、路径冲突、压缩展开预算后再生成新版本，不在每次运行时递归自动解压。

激活技能时返回两个不同概念：

- 文档读取地址：现有 skill:// URI，用于 skill_read。
- 容器内资源目录：例如 /skills/<name>，只读，指向当前任务固定版本；不泄露宿主路径。

首次可继续复用 /skill 挂载。确有多技能协作需求时再扩展为多个已授权且固定版本的目录。通用执行和入口执行必须使用同一套路径解析逻辑。

${SKILL_DIR} 不是标准协议。应将真实目录作为激活上下文返回；若提供环境变量，则显式设置，并告诉模型 argv 不会进行 shell 变量展开。仅对已知适配格式支持受控占位替换，不对任意说明文本做全局字符串替换。

增加资源复制或物化能力，把只读模板复制到任务目录供修改。附件 ID 经鉴权解析后放到任务 input，不能让模型猜宿主路径。默认复制用户原始附件；PPT 示例的 --move 不应直接搬走原件。

## 6. 执行能力：同时覆盖现成脚本和任务代码

保留 run_skill_script，执行已发布包内脚本；扩展现有 execute_command 或提供统一的任务执行封装，使它能够运行 Agent 在当前任务中写出的代码。两条入口共享任务目录、资源解析、运行环境、配额、取消和审计，不能各自形成一套不一致的规则。

首期允许受控解释器和平台安装的命令，使用 argv，不要求实现完整 shell 命令解析器。执行权限来自平台与用户配置，不能由 skill 文本自我授权。

注意三个实现细节：

- 当前参数校验拒绝 $、&、反斜杠、换行等，即使 Docker exec 使用 argv。合法 URL 和文本可能被误拒。应按参数用途校验，文本或复杂 JSON 优先通过文件传入；调用 shell 解释器时另作约束。
- 当前 scripts/ 与显式 entrypoints 适合作为严格模式。可以从包内候选脚本生成入口清单，允许管理员为外部包配置入口，不强制大量改写源包；扩展到其他目录必须显式配置。
- 入口清单不能限制脚本内部调用其他代码，也不能代替容器边界。若允许任意任务代码，必须在产品上明确它与严格入口模式的权限差异。

## 7. 运行环境：从一个镜像扩展成可验证的配置

首期只需要 base 与 documents 两种运行环境。base 保留现有解释器；documents 提供经过验证的文档处理库、字体和转换工具。数据分析与浏览器环境有真实需求后再独立增加，避免首期构建一个覆盖所有用途的大镜像。

文档环境候选依赖包括 python-pptx、python-docx、openpyxl、Pillow、lxml、PDF 处理库；SVG 渲染器、Office 转换器、LaTeX、中文字体按实际包需求确定，不把候选列表当作 ppt-master 的已确认依赖。

运行配置标识由平台映射到允许的 image digest，模型和技能不能自由提交镜像地址。记录技能版本、运行环境 digest、依赖锁文件和构建日志。现有 Dockerfile 可作为共同构建入口，部署文档也要同步调整。

首期采用预装依赖。后续若外部包差异明显，再增加构建阶段的依赖安装：解析声明 → 隔离构建容器安装 → 固定产物 → smoke test → 发布。构建缓存至少按基础镜像 digest、依赖锁和 CPU 架构区分。

不必一开始开放对话中任意 pip/npm。无外网运行不妨碍构建时装包；两种网络权限应独立管理。

## 8. 能力预检：ready 必须有事实依据

当前 reportSkillRuntimeCompatibility 主要检查 manifest、工具名和少量脚本文本模式，未验证实际镜像库、二进制、字体或工作流分支；service 的 load/list 当前也没有向它传入实际工具清单。现有 ready 不能解释为整个技能已经可运行。

预检分两层：

1. 静态检查：入口与引用文件是否存在、资源是否完整、是否包含待展开 ZIP、依赖声明、平台专有工具名、可能的联网脚本。扫描结果只是提示，不能证明脚本行为。
2. 受控运行检查：在目标镜像中验证解释器、声明的库/命令/字体，并运行已配置的 smoke test。构建或隔离验证阶段运行，不在宿主直接执行导入代码，也不为每次列表请求启动容器。

展示“说明可读 / 离线核心可运行 / 缺少某项能力 / 未验证”，并列出具体缺项。按功能分支报告，例如离线导出可用，AI 配图不可用；不要因为可选生图缺失就隐藏整个技能，也不要把未声明依赖的包标为完全就绪。

实际可用性还要结合当前用户工具权限、功能开关、镜像可用性和配额。requiredTools 仅是声明，不是授权。

## 9. 公开网络和外部模型能力

首期复用 web_search / web_fetch，让模型搜集资料后将结果写入任务 input，再由离线脚本处理。增加受控文件下载能力，工具返回工作区路径与元数据，而不是只能给一个网页链接。

生图、图片搜索通过平台工具按需增加，服务凭证留在服务端。原 skill 的 image_gen.py / image_search.py 若直接调用供应商 API，必须改成显式工具调用或提供专用适配器；工具名映射本身不足以改变程序行为。

只有明确出现大量不可改写联网脚本需求，再评估受限出口代理。不要把 network=server-tools 改成“允许全部脚本联网”，也不要为了离线 PPT 首期引入通用 HTTP 代理。

## 10. 长任务、交互与预览

现有技能容器每次执行后销毁，默认 60 秒、最多 120 秒，内存 384MiB，CPU 0.5 核。这适合短脚本，不适合长期预览服务器，文档渲染也可能超限。

首期仍用短生命周期容器；每一步读写持久任务目录，环境变量由平台显式传入，不依赖上一次 shell 的激活状态。按环境设置可配置资源预算，并用代表性任务实测后定默认值。不要承诺简单增加库后所有导出都能成功。

流程进度写入任务状态：taskId、阶段、固定技能版本、固定环境、确认记录、输入与产物。涉及用户等待时先持久化，下一轮按原任务恢复；不要依赖一个一直活着的容器保存状态。普通 skill 先由 Agent 按说明组织，不要求每份 Markdown 都改写成 Mastra Workflow。

PPT 示例有八项确认和串行生成要求。首期通过已有 ask_user 与任务状态维持；如果产品承诺“禁止越过确认执行”，则需要工具执行层检查结构化阶段与确认记录，提示词中的 BLOCKING 不能作为硬保证。

预览分期：先交付静态 SVG/PNG/HTML，再加截图给视觉模型复核，最后才做有 TTL、鉴权路由和清理机制的交互预览服务。只读静态预览不足以满足示例中的 live preview / 标注 / 浏览器编辑，必须展示为明确的降级或适配路线；严格原流程需要等这些能力完成。

## 11. 产物与作用域

复用现有文件下载系统，扩充产物元数据：文件路径、名称、MIME、大小、内容版本、用途与预览信息。将 PPTX、PDF、XLSX、DOCX 等产物作为可下载文件展示，不仅返回 stdout 中的一段路径。

当前 runner 用“执行前后文件名差集”识别新产物，会遗漏覆盖更新的同名文件，也会把中间文件列入结果。优先由脚本/适配器返回产物清单，平台校验文件确实存在且在任务范围内；兼容旧脚本时辅以文件变更检测。

成功至少区分：工具调用成功、进程退出成功、目标产物验证成功。当前 SkillResult.ok=true 时 exitCode 仍可能非零，前端和 Agent 不应据此宣布任务完成。

另一个实际边界：文件工具禁止跨会话访问，但容器当前挂载整个用户 workspace。若要实现同等会话隔离，应挂载当前任务目录与显式授权输入，而不只限制 cwd。此改动与路径适配一起设计，避免破坏现有 scope: workspace 的明确授权用法。

## 12. 实施顺序与验收

| 阶段 | 工作 | 可验证结果 |
| --- | --- | --- |
| P0：形成准确清单 | 获取完整 PPT 包，检查资源、依赖和外部调用；补能力预检 | 给出各分支可用性、缺项与适配清单，无需先开放网络 |
| P1：离线通用闭环 | documents 环境、资源与附件物化、路径绑定、入口配置、任务代码执行、产物交付 | PPT / Word 或 PDF / 表格至少三类端到端样例；不只测标准库 demo |
| P2：流程与公开素材 | 持久任务状态、等待恢复、公开文件下载、静态预览与视觉检查 | 中途刷新或确认后继续；公开素材能进入最终文件 |
| P3：按需增强 | AI 生图与搜图适配、依赖构建缓存、浏览器截图、交互预览 | 完成对应分支的专门验收；不影响已发布离线能力 |

PPT 首个验收应选取明确的离线路线：输入实质性文本 → 完成用户确认 → 创建任务项目 → 逐页生成 SVG → 运行实际质量检查与后处理 → 导出 PPTX → 下载并验证内容与视觉。若原技能将 live preview 作为硬门禁，必须提供兼容预览或将适配版明确标为“离线导出模式”，不能跳过门禁后宣称原包完整兼容。

另外验证：附件转换、中文字体、同名产物更新、非零退出、超时取消、跨任务路径、任务恢复固定版本。文档仅有修改不需运行整套工程测试；实现时应按所变更的链路执行有代表性的容器集成测试。

## 13. 对应代码位置

- src/mastra/skills/package.ts、validation.ts：包解析、外层 ZIP、导入限制与引用检查。
- src/mastra/skills/types.ts、runtime.ts、service.ts：可选运行配置、兼容性报告、环境预检结果。
- src/mastra/skills/script-runner.ts、script-container.ts：执行入口、参数、资源预算、挂载和产物。
- src/mastra/sandbox/manager.ts、docker/provider.ts、docker/client.ts：通用执行复用和任务作用域。
- src/mastra/files/：附件物化、资源复制、产物下载和 MIME。
- sandbox/Dockerfile、docs/deployment/agent-skills.md：可重复构建环境与部署策略。
- src/mastra/index.ts：按仓库规则统一注册新增工具、Agent 或 Workflow。

不建议本轮重写整个 skill UI、移除版本 pin，或直接切换到 Mastra 原生技能自动工具。新增能力应接在现有治理之后。
