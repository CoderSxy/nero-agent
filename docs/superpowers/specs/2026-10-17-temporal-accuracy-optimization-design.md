# Agent 时效信息准确性优化方案

日期：2026-10-17  
状态：方案已确认，A/B/C 已实施，D 暂缓。验证结果见 `docs/temporal-accuracy-verification.md`。

## 目标与范围

改善“今天、近七天、这个周末”等问题的日期解释与数据覆盖准确性。先建立适用于天气、新闻和财经的通用时间基准，再以天气结构化查询完成可确定校验的闭环。

成功意味着：Agent 能说明采用的绝对日期范围；不会将网页中的“今天”直接当成当前日期；天气数据缺日、错日或时区不一致时不会声称已经得到完整七天预报。

保持现有无网命令沙箱。第一阶段不增加数据库字段、前端时区设置或新的外部服务。已有未提交的移动端改动不属于本方案。

## 方案选择

| 路线 | 收益 | 局限 | 结论 |
| --- | --- | --- | --- |
| 只补提示词 | 改动小，立即给模型可信的日期基准 | 无法确定性阻止缺日、错日数据被交付 | 作为第一、二阶段 |
| 通用时间基准、校验纪律，再增加结构化工具 | 通用问题先受益，天气逐步获得代码校验 | 需要分阶段建设 | 推荐 |
| 开放沙箱网络，由模型自行编程联网 | 接近参考项目的工具自由度 | 仍然依赖模型选源和自检，扩大改动范围 | 本次不采用 |

## 阶段一：统一运行时的时间基准

### 行为

- 普通聊天默认使用 `Asia/Shanghai`；后续如增加用户时区设置，再扩展优先级。
- 定时任务使用任务已有的 `timezone`，以实际执行时刻解释“今天”；计划触发时间仅用于调度记录，不代替实际当前时间。
- 每次 Agent 执行开始时生成新的时间快照。同次执行的提示词和工具共用该快照，下一轮重新生成，不从进程启动时间、旧会话或前端持久复用的上下文读取旧值。
- 快照包括 UTC 时间、带偏移的本地时间、IANA 时区、本地日期、星期及生成时间。服务端生成当前时间，客户端只可提供经校验的时区偏好。
- 注入主 Agent 系统提示词，说明相对日期以该基准为准，历史消息及检索文案不能覆盖此基准。
- 若一次任务跨越当地午夜，下一次时效取数前刷新时间基准、重新确认日期范围；固定日期的用户请求保持固定日期。

示例：

```text
当前时间：2026-10-17T09:30:00+08:00
时区：Asia/Shanghai
今天：2026-10-17，星期六
相对日期以本时间基准为准；网页中的“今天”需要核实实际日期。
```

### 拟改动位置

- 新增 `src/mastra/temporal/context.ts`：生成、格式化、校验时间上下文，支持注入测试时钟。
- 修改 `src/mastra/agents/agent.ts`：接入统一时间上下文并注入 instructions。
- 修改 `src/mastra/scheduled-tasks/hooks.ts`：将已有任务时区带入本轮执行。
- 如需 input processor，在 Agent 统一入口初始化执行级快照；具体生命周期以已安装 Mastra 版本文档和集成测试为准。不能只在 HTTP 中间件处理，否则可能遗漏定时任务和直接 SDK 调用。

### 验收

- 同一 UTC 时刻在上海与纽约得到各自正确的本地日期。
- 北京时间凌晨即使 UTC 仍是前一天，也不出现“今天少一天”。
- 同一会话第二天再次提问，日期随执行刷新。
- 普通聊天、Studio、直接 SDK 调用和定时任务均能获得时间上下文。

## 阶段二：明确相对日期和时效取数规则

### 行为

在统一提示词中增加精简规则，不建设通用自然语言日期解析器：

1. 调用时效工具前，先确定目标地点、历史/未来方向、时区和绝对日期范围。
2. 用户指定的明确日期优先于默认解释。
3. “未来七天”默认含今天，共七个当地日历日；“过去七天”默认不含今天，取此前七个完整日历日。用户明确要求含今天时按其要求。
4. 天气场景中无其他线索的“近七天”默认解释为含今天的未来七天，回答开头说明这一假设。含“回顾、历史、下了多少雨”等线索时按历史问题处理；方向仍不明确且影响结果时简短询问。
5. “这个周末”按周六、周日解释；周末当天询问时指本周末，周日可以包含已过去的周六，必须明确日期并区分历史与预报，不能自动当成连续两天未来预报。
6. 优先获取能返回明确有效日期的数据。检索结果中的“今天/明天”必须核对年月日，不能仅凭相对文案拼表。
7. 日期冲突、覆盖不足时读取原始来源或换源；无法核实时明确说明缺失，不补造数据、不平移旧预报的日期。

例如以 2026-10-17 为当地今天：未来七天为 10 月 17—23 日；过去七天为 10 月 10—16 日。

地点类数据另有“目标地点时区”：上海用户查询纽约天气时，预报日应以纽约当地日历组织，回答说明采用纽约时区。用户若明确要求按北京时间展示，需单独转换并解释，不混用两种日界线。

### 拟改动位置

- 新增 `src/mastra/temporal/instructions.ts`，集中管理日期与时效信息规则。
- 修改 `src/mastra/agents/agent.ts`，组合时间基准与规则，避免继续扩大主文件中的内联提示词。

### 验收

- 固定时钟的对话评估覆盖“近七天、未来七天、过去七天、这个周末”、跨月和跨年。
- 注入写有“今天 15 日”的旧摘要，模型不能将其当成 17 日的完整预报。
- 用相同模型、相同问题、全新会话比较修改前后效果，避免历史记忆和模型差异混淆结论。

## 阶段三：建立日期覆盖校验与失败处理

### 分清两种保证

- 对任意网页或自然语言回答：通过提示词要求模型核查，配合受控评估发现问题；不宣称已经由程序保证。
- 对结构化日序列：使用纯函数校验器确定性判断。此阶段用固定数据测试校验器，阶段四接入真实天气工具。暂不在所有回复上增加模型审查器，也不用正则扫描任意回答表格。

### 校验规则

校验输入包含预期的起止日期、时区和返回日序列。检查日期格式合法、首尾符合请求、日期连续、不重复、每日字段对齐、数值合法、必需字段是否缺失。按日历日生成期望序列，不用每次加 24 小时处理有夏令时的当地时间。

时间覆盖与数据质量分别报告：七个日期齐全但某天温度为空，不能标记为完整可用；发布日期存在也不代表预报覆盖正确。结构化数据应附带地点、坐标、时区、获取时间、来源，以及供应商提供时才填写的更新时间。

校验失败返回明确状态，如 `DATE_RANGE_MISMATCH`、`MISSING_DATES`、`DUPLICATE_DATES`、`MISSING_VALUES`。工具不能返回成功状态后仅在文本中附一条警告。

允许一次有针对性的纠正请求。仍不满足时返回部分数据或失败，并在回答中说明真实范围；不无限重试，不自动修改日期凑满七天。

### 拟改动位置

- 新增 `src/mastra/temporal/date-range.ts`：根据明确的起止日期生成、校验日序列。
- 新增对应单元测试。此阶段不将它包装成工具强迫模型调用。
- 使用已有 observability 记录基准日期、目标范围、数据实际范围、来源和校验状态；只记录必要诊断字段，不新建日志平台。

### 验收

固定数据覆盖：昨天起始、少一天、重复一天、日期乱序、跨月、闰日、字段长度不一致、空值、超时及无可用来源。是否允许乱序数据排序后恢复应明确：仅日期唯一且所有字段按记录绑定时可排序，不移动日期与数值的对应关系。

硬性通过标准：错误结构化数据不得标记为完整成功。

## 阶段四：增强取数工具

### 4A：通用搜索增强

扩展 `src/mastra/tools/tavily-search-tool.ts`：

- 保留现有 `query`、`maxResults`，新增可选的 `timeRange`、`startDate`、`endDate` 和 `searchDepth`。
- 保持旧调用兼容，默认仍用 basic，只有需要时升级检索深度。
- 显式请求发布日期，结果增加服务端 `retrievedAt`。来源无法提供发布日期时保留 null，不猜测。
- 校验日期格式、起止顺序；禁止同时提供相互冲突的相对与绝对过滤范围。
- 工具描述明确：时间过滤针对网页发布或更新时间，不代表网页中的天气预报有效日期。不能把未来七天预报范围直接作为网页发布时间过滤范围。
- 默认不强制排除无发布日期来源，避免误删有价值的动态天气页面；它们仍需检查正文有效日期。

同步更新 `tests/tavily-search-tool.test.ts`，验证旧调用兼容及参数映射，不依赖真实 Tavily 余额运行单元测试。

### 4B：天气结构化工具

先使用已有 `web_fetch` 做小范围连通性与响应验证，确认候选 API 的地理编码、时区、预报覆盖和部署使用条件。Open-Meteo 是候选，不在本方案中将其视为唯一供应商。

随后增加一个面向模型的 `weather_forecast` 工具，内部完成：

1. 地名解析；同名地点无法唯一确定时返回候选，要求用户明确，不自行猜测。
2. 确定目标地点时区及日期范围；用户未明确指定时由服务端基于可信时间基准计算。
3. 请求结构化预报，保留实际日期、单位、坐标和来源信息。
4. 调用阶段三校验器；仅在覆盖和必需字段通过时返回完整成功。
5. 返回部分覆盖或不可用时，模型说明不足，不能用搜索摘要覆盖校验失败。

工具边界只覆盖预报；历史天气请求不能调用预报工具冒充实况。历史工具可另行扩展，当前通过检索获取可核实的历史来源，无法获取时说明限制。

拟新增 `src/mastra/weather/client.ts`、`src/mastra/weather/tools.ts` 及对应测试。在 `src/mastra/agents/agent.ts` 开放工具，并按 AGENTS.md 要求在 `src/mastra/index.ts` 注册。首版不增加天气缓存、多供应商自动路由或沙箱联网。

## 验证、发布与实施批次

| 批次 | 交付 | 验收重点 |
| --- | --- | --- |
| A | 阶段一、二 | 所有入口有正确时间基准，日期语义明确，过期摘要不会轻易覆盖今天 |
| B | 阶段三 | 固定数据校验器拒绝错日、缺日、重复和缺值；明确尚未接入真实数据入口 |
| C | 阶段四 A | 检索提供更充分的时间证据，兼容原工具调用 |
| D | 阶段四 B | 天气工具形成从时间基准、API 取数到覆盖校验的完整闭环 |

按批次验证和发布，保存修改前的固定评估样本。开发时运行有针对性的 `node --import tsx --test tests/<相关测试>.test.ts`；每批完成后运行项目 `npm test` 和 `npm run build`，失败时先确认是否属于原有问题。启动使用 `npm run dev`，不直接执行 mastra dev/build。

模型评估与单元测试分开：单元测试验证确定性规则；对话评估验证模型是否遵守规则。先使用模拟来源保证结果可复现，再使用少量真实请求检查集成；不能把一次真实查询成功视为所有场景可靠。

本方案不承诺提高气象模型本身的预测准确率；改善的是日期解释、来源选择、数据覆盖与如实交付。
